## Step 1: the save bug (Q205, Q209)

### The cause

**The save was sent. It was slow.**

- **What was seen:** Confirm (an undercut's row) and Apply (the method) both send `PUT …/result/{sheet}/lines` at
  once. The page's own request log shows it leaving at 0.7 s.
- **How long the api took:**
  - 36.8 s to answer while the step's full Calculate was saving beside it.
  - 10.6 s for the next one alone.
  - Replayed in-process under a profiler, the captured save took 22.4 s alone (43 s cold).
- **Why that looks like no save:** each save holds the project's row and the starter's lock for its whole
  transaction, so the second waits for the first. c45 step 5 and c44 wait 30 s for the lines and read the delay as
  "no save". Last queue's "no `PUT …/lines` in the api log" was the log lagging: the request was still running.
- **Where the time went:** pricing the site spreads.
  - `sync_sites` priced each site-spread activity with `sync_site`, and each one read every line of the project again.
    For each line it looked up the line's activity by role, its unit and its division, several queries a line.
  - D-822's `site_lines_for` reads them for every activity in one pass, but `sync_sites` never used it.
  - The starter grew from 71 to 104 activities this month (releases 18 to 34), so every save got slower with it. That
    is why c45 step 5 passed on 11-02 and failed this week.
- **Not the cause:** D-999 and D-1005 change no part of the save path.

### The fix (D-1018)

- `sync_sites` reads every site-spread activity's lines once, with `site_lines_for`, and hands each to `sync_site`.
- Pricing a spread writes only its own spread rows, never what the pass reads, so one read serves all.
- **Measured:** the same captured save went from 22.4 s to 4.5 s warm. The quantity table is unchanged (0 FAIL).
